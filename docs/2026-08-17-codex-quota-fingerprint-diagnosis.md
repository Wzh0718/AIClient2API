# Codex 额度、凭据组与指纹收敛诊断

日期：2026-08-17  
范围：只读对照本地 usage 快照、provider 池、凭据组。未改默认、未改生产配置、未做风控对抗。  
账号标识只用 uuid 前 8 位和脱敏邮箱前缀。

## 结论

1. 凭据组不是这次降额的原因。它只决定 Key 打哪个号。
2. 指纹收敛是共同背景，不是区分变量：13/13 Codex OAuth 账号都是 `session` + `codexFingerprintMigrated=true` + version 1。
3. 本地指纹上线与官方重置撞在同一天，时间线不能定因。
4. 能分开的是「上限变小」和「消耗变快」。部分号的隐含周限明显塌缩，部分号没有。这支持用户说的「只有部分号被砍」。
5. 官方 usage 页的客户端类型（cli / desktop）本地缓存里没有，无法核验社区那条「全变成 cli」。

## 指纹诊断

[docker-data/configs/provider_pools.json](../../docker-data/configs/provider_pools.json) 现况：

- 13/13 `codexFingerprintMode=session`
- 13/13 `codexFingerprintMigrated=true`
- 13/13 `codexFingerprintVersion=1`

这与 sub2api v0.1.175 的静默默认同构，也与他们后来在 PR #5610 改回 `off` 的理由同构。因为全池同模式，**不能**用指纹模式解释「谁被砍、谁没被砍」。

出口不是单 IP：4 个 clash proxy id，分别挂 5/3/3/2 个号。被砍迹象更明显的 outlook 号分散在其中 3 条出口上，所以也不是「某一条代理单独出问题」。

## 上限变小 vs 消耗变快

官方缓存只给百分比，不给周限绝对数字。用「当周 token / 周百分比」估隐含容量。  
限制：token 来自 calendar week bucket，百分比来自官方 rolling window，只能看数量级，不能当发票。

## 凭据组与负载

凭据组 08-14 才应用，晚于 08-13 的指纹上线和部分号触顶。它解释不了 08-13 当晚的 100%。

当前 revision 2（08-16）只剩 `62154a7c` 一个组，两个 Key 都是 `auto` 指向它，没有 `fixed`。这能解释这个号 08-17 仍在被打到 99%，解释不了更早那批 outlook 号的隐含周限塌缩。

08-14 时三个组分别钉在 `8fb06b25` / `a7fc7a96` / `82aacbd4`。后两个在上表里属于「隐含周限仍高」的一侧。

## 缺什么

- 官方 usage 页客户端类型。本地 usage cache 没有 cli/desktop 分解。
- 13 个号在 08-11 的完整用量。prod-sync 那天只有 2 个成功样本。
- 指纹审计是内存 Map，重启即丢，回溯不了「第一次改写」时间。
- request-audit 当前 latest 计数为 0，帮不上忙。

## 若要做 A/B（你自己改配置，这次不做）

- 不要关全局 `CODEX_FINGERPRINT_ENABLED`：一次关掉全部号，对照作废。
- 选负载接近的一对，例如仍偏高的 `82aacbd4` 和已经偏矮的 `420a8594` 或 `62154a7c`，只把其中一个改 `off`。
- 比完整周窗，不看几十分钟。改 `off` 会断上游 prompt cache，短期 token 会变贵。
- 记录：官方周百分比、当周 token、隐含容量、重置时间、客户端类型是否从纯 cli 变回多类型。
