# Antigravity 模型可用率与冷却展示设计

## 目标

在用量查询页按凭据展示 Antigravity 模型的实时可用率、模型级限流状态和预计恢复时间，并提供显式的“检测全部模型”操作。

## 方案比较

1. 每次刷新用量时自动逐模型请求：数据最新，但每个凭据会额外产生十余次调用，容易反向触发 429，不采用。
2. 只根据模型列表与历史 429 推算：没有额外成本，但不能确认未报错模型当前是否真能响应，不足以称为“测试”，不采用。
3. 手动触发、服务端串行探测并缓存结果：兼顾真实性、成本与安全，采用。

## 数据流

管理员在单个 Antigravity 凭据卡片点击“检测全部模型”。前端调用专用 POST API；服务端解析凭据并复用对应 adapter，通过 `listModels()` 获取该账号实际暴露的模型。仍在冷却期的模型不再次请求，直接记为 `cooldown`；其他模型使用最小提示串行探测，模型间保留短延迟。

探测结果只保存状态、耗时、错误分类和时间，不保存模型输出。结果写入现有 usage cache 的实例节点，字段名为 `antigravityModelAvailability`，普通用量刷新和缓存降级必须保留该字段。

## 状态模型

- `available`：最小请求成功。
- `cooldown`：模型级 429，包含 `scheduledRecoveryTime`。
- `capacity`：503/上游暂时无容量，可重试但不计为可用。
- `unsupported`：模型列表不支持或请求明确返回模型不存在。
- `error`：其他错误。
- `skipped`：凭据禁用、已有有效冷却或探测被取消。

汇总返回 `totalModels`、`availableModels`、`availabilityPercent`、`checkedAt` 和逐模型结果。可用率按 `available / totalModels` 计算；处于冷却、容量不足或错误的模型都不算当前可用。

## UI

账号健康和模型健康分层显示：账号仍可为“健康”，但模型区显示“可用 14/16（87.5%）”。异常模型逐行展示状态、最近错误和本地化恢复时间；有恢复时间时显示倒计时语义。没有做过全量探测时，仍根据现有 `antigravityQuotaHealth.models` 展示模型冷却，不伪造可用率。

## 安全与边界

- API 仅允许 `gemini-antigravity`。
- 只接受服务端已有 UUID，不接受凭据内容。
- 默认并发固定为 1，不允许前端提高。
- 有效冷却模型必须跳过。
- 不自动周期探测，不因打开页面产生模型请求。
- 不修改生产配置或部署。

## 验收

- 服务端能对 mock adapter 的模型列表完成串行探测并正确分类。
- 429 可展示模型名与恢复时间，账号整体健康不被错误改为异常。
- 使用缓存和单实例刷新时保留最近一次模型探测结果。
- UI 能显示可用率、异常模型详情，并能手动触发探测。
- 现有 Antigravity 用量、额度和冷却测试继续通过。
